🧪 Metodologia de Testes • Padrão ILC Integrator

Qualidade como Pilar Estratégico: Shift-Left, BDD e TestOps

No ecossistema ILC Integrator, a Qualidade de Software não é uma etapa final de inspeção, mas uma disciplina contínua aplicada desde a concepção dos requisitos (Shift-Left Testing). Adotamos a abordagem dos Três Amigos (Negócio/Operações + QA + Engenharia de Software) para garantir que cada funcionalidade nasça com critérios de aceite claros, mensagens de validação documentadas e testes rastreáveis vinculados às Instruções de Trabalho (ITs) oficiais.

🤝 Sinergia: Como o Docs Hub e o Azure DevOps se Complementam

A estratégia de qualidade do ILC Integrator opera em dois pilares integrados que se alimentam mutuamente: o Docs Hub (este portal) como a Fonte Única da Verdade para consulta e treinamento, e o Azure DevOps como o Motor de Execução, Gestão Ágil e Rastreabilidade.

📐 O Padrão Definitivo da Tab 2 (Qualidade QA) nos 19 Módulos

Todo módulo presente no ILC Integrator segue rigorosamente a Metodologia de 7 Seções de QA, garantindo consistência e completude para os analistas:

1
Metadados & Criticidade do Módulo

Define a criticidade operacional (Alta/Média/Baixa), alçadas financeiras de aprovação, SLAs de testes e link direto para a Instrução de Trabalho (IT) normativa.

2
Roteiro Passo a Passo de Testes Manuais

Guia detalhado numerado de execução com pré-condições, passos operacionais em tela, dados de teste a preencher e evidências formais esperadas (prints, logs ou toasts).

3
Matriz de Validação & Mensagens Reais de Erro

Tabela exaustiva mapeando: Campo de Tela ➔ Validação Aplicada ➔ Regra de Negócio ➔ Mensagem Real de Erro exibida pelo Sistema ➔ Ação Corretiva.

4
Critérios de Aceite & Definition of Done (DoD)

Checklist mandatório de qualidade contendo requisitos funcionais, não-funcionais, segurança de alçada e auditoria que devem ser 100% cumpridos antes da aprovação.

5
Especificação BDD em Gherkin (Dado / Quando / Então)

Cenários de comportamento (Caminho Feliz, Exceções de Negócio e Validações de Alçada) em linguagem natural estruturada, prontos para automação com Cucumber/Playwright.

6
Matriz de Rastreabilidade & Gestão de Riscos

Mapeamento bidirecional conectando: Requisito de Negócio ➔ IT Normativa ➔ User Story no Azure DevOps ➔ Casos de Teste (Test Cases) ➔ Nível de Risco Operacional.

7
Checklist de Regressão & Homologação

Conjunto enxuto de verificações obrigatórias de regressão (Smoke Test) para validar que novas alterações no módulo não quebraram fluxos adjacentes da esteira logística.

🐛 Gestão de Defeitos & Classificação de Severidade no Azure DevOps

Critérios formais para registro de bugs no Azure DevOps Boards durante as baterias de homologação:

Severidade Critério de Impacto Exemplo no ILC Integrator Ação / SLA
🔴 1 - Bloqueante Impede totalmente a execução do fluxo operacional, indisponibilidade de tela ou corrupção de dados. Sem contorno (workaround). Erro 500 ao salvar Frete Expresso; impossibilidade de aprovação de alçada de viagem. Correção Imediata (Hotfix) • Bloqueia Deploy
🟠 2 - Alta Inconsistência funcional grave em cálculos, alçadas ou dados fiscais, mas existe contorno operacional temporário. Cálculo incorreto de alíquota de pedágio em rota específica; falha no envio de e-mail de alerta. Correção na Sprint atual • Impede Release Major
🟡 3 - Média Falha de validação secundária, comportamento divergente de layout que não impede a conclusão da tarefa. Filtro de busca por data não mantendo o valor selecionado após paginação da tabela. Correção na próxima iteração / backlog planejado
🔵 4 - Baixa Ajuste cosmético, desalinhamento visual leve, erro ortográfico em rótulos ou melhoria de usabilidade. Label de campo desalinhada 2px; texto de tooltip com erro gramatical menor. Backlog de melhorias contínuas

✅ Definition of Ready (DoR) & Definition of Done (DoD)

📋

Definition of Ready (DoR) — Entrada

Critérios obrigatórios para que uma User Story seja considerada pronta para desenvolvimento:

  • Vinculação expressa à IT normativa correspondente.
  • Critérios de aceite definidos em formato BDD (Given/When/Then).
  • Mensagens de erro e validações de tela mapeadas.
  • Massa de dados de teste e permissões RBAC identificadas.
🏆

Definition of Done (DoD) — Saída / Deploy

Critérios mandatórios para autorizar a liberação de release para Produção:

  • 100% dos Test Cases do Test Plan executados com sucesso em Staging.
  • Zero bugs de Severidade 1 (Bloqueante) ou 2 (Alta) em aberto.
  • Bateria de Regressão (Smoke Test) aprovada sem quebra colateral.
  • Aprovação formal e evidências anexadas no Azure DevOps.
